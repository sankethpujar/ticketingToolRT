# Rangatantra tickets

Event reservation and physical ticket issuance desk. Responsive React interface, server-side role checks, username/password sign-in and Cloudflare D1 persistence.

## Accounts and roles
- Super user: sole account creator; all application operations and role changes.
- Admin: create/close/delete events, all booking/counter operations, and promote existing RT_Users to Admin. Cannot create accounts or change the super user.
- RT_User: reservations, payments, issuance and reports. No event or user administration.

Usernames are case-insensitive identifiers (3–40 letters, digits or underscores); no email required. Passwords are salted PBKDF2-SHA256 hashes. Random server-side sessions expire after 8 hours and use Secure, HttpOnly, SameSite cookies. Sign-out invalidates the current session. Login attempts are limited per username/IP over 15 minutes.

The initial super account is `admin_RT`. Its bootstrap hash and salt are configured only through the runtime secrets `RT_BOOTSTRAP_HASH` and `RT_BOOTSTRAP_SALT`; never commit passwords or these values. Bootstrap inserts only a missing super account and never resets an existing account. Old ChatGPT users remain in the legacy state for rollback, but cannot authenticate in this version. Authentication uses separate D1 tables.

Restore point: GitHub branch `backup/chatgpt-login-2026-10-16`, hosted version 9. Restoring that source also requires restoring owner-private hosting access before deploying the old ChatGPT-auth version. This is a code restore point, not a frozen copy of booking data.

## Workflows
Create an event (name, code, date, venue, ticket price), register a reservation with an optional phone, then search by reference/name/phone at the counter. Booking numbers use EVENTCODE-DDMMYY-001 with an event-local sequence. Partial issuance cannot exceed the outstanding quantity. Payments apply to an entire booking. Unpaid bookings require full payment confirmation before issuance.

Records are stored centrally in D1. Version-checked updates reject concurrent stale changes and require retry, preventing duplicate issuance and reference collisions. This initial small-scale implementation stores versioned application state in one row; normalization and scale testing belong to the NFR phase.

## Development
Use Node 22.13+; install dependencies and run `npm run dev`. Sites provisions the D1 binding DB. Generate schema migrations with `npm run db:generate`; production migration application is part of deployment.

Validation: `node node_modules/typescript/bin/tsc --noEmit`, `node tests/desk.test.mjs`, and the Sites build helper. Authentication and desk tests use an in-memory SQLite database behind the D1 interface. Browser QA remains a separate check.

## Pending
Optional event image gallery; editable event pricing; booking cancellation and quantity edits; invitation onboarding; per-ticket pricing/refunds/partial payments; NFR review. Existing booking prices are captured at registration.

## Soundboard
The Soundboard navigation item opens a browser-local scene-by-scene cue board. Team members can add/edit scenes, choose local sounds for the within-scene or post-scene columns, and edit cue names. Drop one or multiple audio files onto a scene’s Sounds Within Scene area to create named cue buttons. Each scene supports at most six within-scene sounds, counting existing cues. A drop that exceeds the limit or includes invalid audio is rejected in full with a dialog; no partial batch is saved. Batch metadata and audio are committed in one local transaction. The Add local sound dialog enforces the same limit. Post-scene music remains separate. New sound names default to the selected file name without its extension; operators can edit them. A manually entered name is preserved when changing the selected file, and replacing an existing cue’s audio keeps its label. Clicking a sound selects it with a thick maroon outline. After the initial mouse selection, arrow keys move to the nearest sound in that direction across scene sounds and post-scene music, scrolling the cue into view. Arrows do not choose an initial sound or start playback; Space plays the selected sound. Each card also has a bottom-right play/stop control. Escape fades all playing sounds out over one second, then stops and rewinds them (outside text fields/dialogs). Volume is restored for the next play. On-screen Stop controls stop immediately; new sounds started during a fade are unaffected. A ten-level master volume bar sets 10% through 100%, using click or keys 1–9 and 0 for 100% (outside text fields/dialogs). It controls current and future playback and defaults to 100%. Volume changes preserve the one-second fade envelope. Only one cue can load/play/fade at a time. Selecting a different cue remains possible; Space or its play control shows a brief warning until the current cue ends or is stopped. The active scene row has a saffron tint, maroon left strip and a status badge, including post-scene music; the highlight clears when playback ends or the fade completes. Letter/number shortcuts are no longer used. The outward-arrows Fullscreen control expands the Soundboard to fill the browser viewport using an in-page overlay. X or x (outside text inputs) or Exit returns to the normal page. Browser chrome remains visible. Native browser fullscreen is intentionally not used because browsers reserve Escape to exit it; in expanded Soundboard view Escape only fades/stops the audio. Playback continues through fullscreen changes. Playback is on the operator's device and stops when leaving the page.

Scenes, cue settings and audio are stored only in IndexedDB in the selected browser, scoped to the signed-in app user and site origin. Nothing from the Soundboard is synced to the server. New cues and their audio are saved together in one transaction. Set up the board on each device; old server boards are not imported. Adding/editing scenes and choosing audio work without internet after the page is open. Playback uses local blob URLs, and the readiness banner counts loaded cues. Open the page online and keep the tab open for offline playback; offline app reopening is not implemented. Clear soundboard shows a confirmation, stops playback and atomically removes the current account’s local scenes, settings and audio (including orphaned older local audio). It does not affect original files or other users’ boards. Reloads retain the board until explicitly cleared.

There is no fixed app file-size limit for local audio; available browser storage applies. Supported extensions are MP3, WAV, OGG, M4A, AAC, FLAC and WebM; playback depends on browser codec support. Clearing site data or browser eviction can remove local copies, so retain originals. The old server audio upload and playback endpoints return HTTP 410. Previously uploaded R2 audio objects are preserved, not automatically deleted; Plays PDF storage remains unchanged. Server scene/cue writes also return HTTP 410; legacy server metadata is omitted from desk responses and left untouched in storage. The scene list scrolls vertically and the three-column layout scrolls horizontally on smaller screens.
